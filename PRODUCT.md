# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack

delegated: Go API with a React + TypeScript + Vite dashboard; the backend owns real concurrent experiment behavior and the browser consumes REST and Server-Sent Events.

## Users

Software engineers, systems students, and portfolio viewers who want to understand what happens when a backend receives more work than it can process.

## Product Purpose

Backpressure Lab lets a user configure and run a small backend experiment, deliberately push it beyond capacity, and observe queue depth, throughput, latency, failures, timeouts, and downstream pressure as they emerge. Success means the relationship between offered load, finite capacity, overload, and recovery is understandable within one short run.

## Positioning

The product is an interactive systems debugging instrument: its dashboard is driven by actual concurrent work, queues, deadlines, and a synthetic dependency rather than a prerecorded animation.

## Operating Context

A visitor opens the public lab, chooses a built-in scenario, starts a run, watches the pipeline and live metrics, then inspects the terminal summary. The first slice uses ephemeral in-memory experiments and is safe to run locally or as a bounded public demo.

## Capabilities and Constraints

- Phase 1 includes healthy, traffic-spike, slow-dependency, and dependency-failure scenarios.
- The baseline profile intentionally has no user-facing overload protection; a generous internal queue cap protects the host and is reported as a safety cap.
- The system must show where requests wait, execute, fail, time out, or are rejected.
- Phase 1 does not include retries, protection strategies, comparison mode, persistence, accounts, or arbitrary external targets.
- Metrics are aggregate snapshots; raw per-request traces are not required for the first slice.

## Brand Commitments

The name is Backpressure Lab. The product should feel like a precise systems instrument rather than a generic monitoring dashboard or game.

## Evidence on Hand

The evidence is generated by the running experiment. No customer, performance, pricing, or production-capability claims may be invented.

## Product Principles

- Show the mechanism, not a decorative simulation.
- Make capacity and tradeoffs legible at a glance.
- Preserve enough realism for metrics to teach something true.
- Make the first experiment runnable with sensible defaults.
- Explain state changes in concise operational language.

## Accessibility & Inclusion

The web dashboard must support keyboard operation, visible focus, readable contrast, semantic status text, reduced motion, and a responsive layout without relying on color alone.
